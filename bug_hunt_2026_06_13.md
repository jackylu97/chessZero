# Draw-Basin Bug Hunt — Pass 4 (Self-Play Data Pipeline)

Investigation date: 2026-06-13
Method: 8-dimension parallel fan-out audit (Opus 4.8), every hypothesis backed
by an executed probe through the real code on CPU/GPU; every candidate finding
adversarially verified by an independent agent instructed to refute it. Probe
scripts written under /tmp/bugbash/ (not committed). No code was changed; the
live training run (`2026_06_12_lr1e3_buf2x`) was not disturbed.

Scope: bugs that could explain the residual draw basin AFTER the Pass 1-3 fixes
(STM encoding, past-terminal masking, per-sample value_loss_weight, inverse
dynamics, decisive resampling) — i.e. genuine code defects (sign/POV/index/
masking/arithmetic errors), not design opinions.

**Headline:** the three confirmed mechanical contributors are all in the GPU
self-play data pipeline, NOT in the architecture or the recently-rewritten STM
encoding. Two corrupt the policy target on the production path; one floods the
buffer with artificial draw labels.

## Confirmed bugs (ranked)

### A. `select_action_gpu` applies temperature per duplicate slot, not per unique action — HIGH, NEW
**Location:** `src/mcts/tensor_mcts.py:88-121` (production GPU-resident self-play path).

Under `sample_k=50`, the same action is sampled into many of the K=50 root
slots, and PUCT materializes a separate child subtree per slot, so an action's
total visits are SPLIT across its duplicate slots. The numpy reference path
(`_build_compat_roots`, `tensor_mcts.py:1290-1303`) SUMS visits across duplicate
slots (np.unique / np.add.at) BEFORE `select_action` applies temperature. The
GPU path does the opposite: it computes `slot_probs = softmax(log(per_slot_visits)/T)`
over the raw K slots and only `scatter_add_`s duplicate slots together AFTER the
softmax. Because `softmax(.../T)` is nonlinear for T≠1:

```
Σ_dup softmax(log(v_slot)/T)  ≠  softmax(log(Σ_dup v_slot)/T)
```

Two corruptions, both on the production path (`use_gpu_resident_self_play=True`):
1. **Policy training target** (dense, written to `history.policies` via
   `self_play.py:521/598`) is wrong.
2. **Action selection** picks the wrong move — it sharpens toward the
   highest-visit *slot*, not the highest-total-visit *action*.

**Evidence:**
- Minimal: `child_actions=[10×7, 20]`, `child_visits=[4×7, 20]` (action 10 = 28
  total visits, action 20 = 20). At T=0.1 the GPU path selects action 20 and
  emits dense `p(20)=1.0`; the correct dedup path selects action 10 with
  `p(10)=0.9666`. The GPU path trains toward the LOWER-total-visit action.
- Real `run_batch_gpu` (GPU, fp16, flat value head): max |gpu−ref| policy-target
  divergence 0.68 @T=0.1, 0.32 @T=0.25, 0.11 @T=0.5; matches exactly @T=1.0
  (softmax linear there).
- N=64 real games, T=0.1: GPU picks a sub-optimal-by-visits action in 56/64
  (88%).
- Duplication is the norm, not an edge case: at K=50 from ~30 near-uniform
  legals, 25-44 of 50 slots are duplicates.

**Draw-basin mechanism:** in the flat-value (collapsed) regime PUCT spreads
visits evenly across duplicate slots, so the per-slot softmax produces a
near-UNIFORM policy target — actively manufacturing high-entropy targets exactly
when the value head is flat, opposing policy sharpening and reinforcing the
prior/draw loop. Tests stay green because they exercise the dedup-correct numpy
path; all GPU self-play data is generated wrong.

### B. Policy targets use the sampling temperature instead of raw visit counts — HIGH
**Location:** `src/mcts/mcts.py:678` + `src/training/self_play.py:115/198/319/531`.

`select_action` / `select_action_gpu` return the temperature-adjusted
distribution `visits^(1/T)` (equiv. `softmax(log(visits)/T)`), and all self-play
loops store that verbatim as the CE policy target; `make_target` consumes it
directly. The chess preset uses `temperature_final=0.1` after `temperature_drop_step=30`
plus `temperature_schedule=[(0.5,0.5),(0.75,0.25)]`, so every policy target from
ply 30 onward is `visits^10` ≈ one-hot at argmax-visits.

This is a genuine bug, not a design choice, proven internally:
- The function's own docstring (`mcts.py:659`) claims it returns "raw-normalized
  visit counts N(a)/ΣN(a)".
- The reanalyze path (`trainer.py:899`) deliberately calls
  `select_action(root, temperature=1.0)` with the comment "raw visit-count
  normalization" — so the same network is trained on two inconsistent target
  definitions depending on whether a position came from fresh self-play
  (sharpened) or reanalyze (raw).
- Reference implementations (MuZero pseudocode `store_search_statistics`,
  muzero-general, Lc0) store raw visit fractions and use temperature for action
  SELECTION only.

**Evidence:** real `select_action` / `select_action_gpu` on visits [60,50,40,30,20]:
raw target [0.30,0.25,0.20,0.15,0.10] vs stored target @T=0.1 [0.8476,0.1369,
0.0147,0.0008,~0]; entropy 1.544→0.480 nats; CPU and GPU paths bit-identical.

**Draw-basin mechanism:** with a flat value head visits mirror the prior, so
full-weight CE toward ~one-hot(argmax(prior)) collapses policy entropy onto the
current argmax — the "visits mirror prior, never escapes" symptom — and discards
the graded visit-ordering search produces. Reanalyze repairs only 256 games per
1024 steps, after the damage.

**A and B share a fix:** build the policy target from DEDUPLICATED raw visit
fractions `N(a)/ΣN(a)` at T=1.0, decoupled from the sampling temperature (which
should continue to drive only action selection).

### C. GPU engine never detects insufficient material — HIGH, NEW
**Location:** `src/games/chess_gpu.py:1708`.

```python
done = mate | stalemate | seventy_five_move | ply_cap | threefold
```
No insufficient-material term (grep "insufficient" over `chess_gpu.py` → 0 hits).
The CPU engine `ChessGame.step` (`chess.py:155`) uses
`board.is_game_over(claim_draw=False)`, which includes `is_insufficient_material()`,
so K-vs-K / K+B-vs-K / K+N-vs-K draw immediately on CPU.

Production self-play uses the GPU engine; warmstart Stockfish generation,
`evaluate.py`, and `eval_checkpoint_health` use python-chess. So when a self-play
game simplifies to a bare-king endgame (the natural tail of essentially every
non-mate game), the GPU engine does NOT terminate — it plays on until the 75-move
clock, threefold, or the 1024-ply cap, recording `winner=0` the whole way.

**Evidence:** KvK / KBvK / KNvK all show CPU `done=True` / GPU `done=False` at the
insufficient-material position; same-color KB-vs-KB (correctly NOT insufficient)
matches on both engines, proving the divergence is specifically the missing
insufficient-material term. A KN-vs-K start ran 197-226 GPU plies before
terminating via the 75-move clock, all `winner=0`; CPU/eval would label it 1 draw
at ply 0. Across 60 random games / 15,868 plies, all 4 done-mismatches were
insufficient material (halfmove and winner labels otherwise matched exactly).

**Draw-basin mechanism:** large systematic injection (~150-230×) of
low-information `[0,1,0]` draw-labeled positions into the value head's training
signal — a NEW, distinct mechanical cause of the draw-target inflation that
Pass-1 §3 identified as the core driver — AND it desyncs the GPU self-play
draw-label distribution from the python-chess warmstart/eval distribution (eval
reports draws hundreds of plies earlier than self-play does).

### D. Mutating terminal observation for early-finishing games — MEDIUM
**Location:** `src/games/chess_gpu.py:1636-1722` + `src/training/self_play.py:565,604`.

In `_step_batch_impl` the done/winner *flags* are frozen sticky
(`new_state.winner = torch.where(state.done, state.winner, winner)`, line 1722),
but the BOARD fields (`pieces`, `side`, `castling`, `ep`, `halfmove`, `fullmove`,
`ply`) are recomputed unconditionally from the action with NO
`torch.where(state.done, old, new)` gate. So a finished game keeps mutating under
sentinel steps for the rest of the batch. `final_obs = to_tensor_batch(state)` is
captured ONCE at end-of-batch (`self_play.py:565`) and appended as every game's
terminal observation (`:604`), so for any game that finished before the batch's
longest game (most of them, given the 1024-ply cap vs ~347-ply avg), the stored
terminal observation is the true terminal plus hundreds of sentinel moves.

**Blast radius:** one corrupt sample per game — the terminal index. Its value
target is the decisive outcome one-hot ([1,0,0]/[0,0,1] for won/lost games), so
this injects noise specifically into the scarce decisive value samples, which
`decisive_sample_frac=0.5` then oversamples. The per-ply observations of done
games are correctly discarded (history trimmed to `game_length`); only the
end-of-batch `final_obs` is affected.

**Fix:** freeze board fields for done games with `torch.where(state.done, ...)`,
OR capture per-game `final_obs` at the finish ply rather than end-of-batch.

### E. Terminal-root policy target is all-zeros — LOW (benign, already documented)
**Location:** `src/training/replay_buffer.py:279`.

`pos = np.random.randint(0, len(game))` can select the terminal index
(`idx == len(actions)`, since `len(game) == len(observations) == len(actions)+1`).
There `self.policies[idx]` is out of range and falls back to a zeros(A) policy
target → CE contributes exactly 0 gradient. The value target at that index is
correctly computed from STM POV. A zeros target (unlike the harmful past-terminal
uniform filler) pulls nothing, so this is a true 1-entry-per-game no-op — exactly
the edge case noted in `bug_hunt_draw_basin.md` §1 item 3. Not a draw-basin
contributor; recorded for completeness.

## Refuted

**"Single-frame consistency target is off-distribution."** REFUTED with evidence.
The premise — that the single-frame-masked input is a distribution `representation()`
never sees — is false. `_stack_history` (`replay_buffer.py:139-163`) zero-pads
missing earlier frames for early-game positions, and the real ply-0 stack is
BIT-IDENTICAL to the single-frame mask. Self-play feeds the same shape (the GPU
`obs_window` is zero-initialized, `self_play.py:443-445`), and with
`random_opening_plies=8` every game passes through these early plies. The
mostly-zero stack is squarely in-distribution at root inference, in self-play,
and in training targets. The slice itself is correct (newest frame, channels
0-18 of 152; no off-by-one). The high rep(full)-vs-rep(single) dissimilarity is
the documented PURPOSE of `consistency_single_frame_target`, not a defect.

## Cleared dimensions (probed thoroughly, no bug found)

These are reassuring negatives — each was exercised with executed probes.

- **STM-relative encoding** (`chess.py` / `chess_gpu.py`; the highest-stakes
  2026-05-06 change, previously zero-coverage): **CLEAN**. 480,542 move
  encode/decode roundtrips for both colors (incl. promotions, underpromotions,
  castling, EP); 250-position CPU↔GPU observation parity (all 19 planes
  byte-identical); asymmetric castling-plane reorder + EP-flip; underpromotion
  direction under rank-flip; 60-game single + 48-game mixed-color batched
  step-by-step parity; EP-capture execution in mixed batch; and the color-symmetry
  invariant (position vs its mirror → identical core planes + legal sets). The
  board-flip is implemented correctly and consistently across both engines.
  Existing tests (`test_chess_gpu_obs/legal/actions.py`) pass.

- **TensorMCTS tree search** (`tensor_mcts.py` / `tensor_mcts_triton.py`):
  **CLEAN**. Backprop sign/POV (`v[d] = reward − discount·v[d+1]`) matches the
  python loop across discounts and depths; fp16 hidden-state storage roundtrip
  error ~2.4e-4 with 0.0 value/logit drift through recurrent_inference; eager vs
  triton vs compile PUCT backends agree bit-for-bit on visit distributions and
  root_value. The duplicate-slot defect (A) is in `select_action_gpu`, not the
  tree.

- **Reanalyze** (`trainer.py::_reanalyze`, `reanalyze_use_tensor_mcts=True`):
  **CLEAN** on index alignment. The catastrophic off-by-one writeback hypothesis
  was DISPROVEN with a tagged-writeback probe (0 bad writebacks across chunk
  boundaries, both backends) — each batch item carries its own `(game, pos)`
  tuple, so there is no positional drift. Observation reconstruction matches
  self-play stacking byte-for-byte; legal masks are position-matched; no
  Dirichlet noise; amp dtype dispatch correct. (Chess never reads `root_values`
  for value targets under `td_steps=-1`/WDL, so the policy writeback is the only
  consequential one, and it is aligned.)

- **aux-losses / loss assembly** (`trainer.py`, `muzero_net.py`): **CLEAN**.
  Consistency single-frame slice correct (newest frame, channels 0-18); inverse-
  dynamics CE target `actions[:,k]` identical to the action fed to dynamics, and
  masked past terminal; the 0.5 grad hook fires once per step with no closure
  late-binding bug; past-terminal masking (Fix 1) and per-sample `value_weight`
  (Fix 3) implemented correctly; value/policy/inverse CE are fp32-promoted under
  AMP; `value_target_scale`/`value_support_size` correctly dormant in the WDL
  path; `draw_score` only modifies the MCTS-leaf/diagnostic scalar, never the
  training target.

- **targets / make_target** (`replay_buffer.py`): **CLEAN**. `_wdl_target_at`
  parity correct at every ply parity (white-win, black-win, draw; odd/even
  lengths); `random_opening_plies` ARE recorded from ply 0 in all three loops and
  ply 0 is always white-to-move, so the `stm_is_white=(ply_idx%2==0)` assumption
  holds and there is no parity inversion; history stacking is consistent between
  self-play inference and training reconstruction; decisive-resampling batch
  composition matches spec with sane IS weights and graceful empty-stratum
  fallback.

## Recommended fix order (no code changed yet — pending review)

1. **A + B together** (few lines): build the policy training target from
   deduplicated raw visit fractions `N(a)/ΣN(a)` at T=1.0; keep the sampling
   temperature for action selection only. Highest leverage — corrects every GPU
   self-play policy target and move choice.
2. **C** (small): add an insufficient-material check to `_step_batch_impl`'s
   terminal set (and ideally cross-validate GPU vs python-chess in the existing
   harness). Stops the artificial-draw flood.
3. **D** (small): freeze board fields for done games, or capture per-game
   `final_obs` at the finish ply.

None of these are in the architecture or the STM encoding — they are localized
defects in the GPU self-play data pipeline.
